# Configurara GitHub

Para que tus packages “tokens” y “ui” se publiquen bajo la nueva cuenta/organización en GitHub Packages y queden consumibles, lo clave es alinear: scope del paquete, .npmrc, permisos del repo y el workflow. Te dejo un checklist corto y accionable.

## 1) Qué “crear” en GitHub
No se “crean” paquetes manualmente: aparecen automáticamente cuando publicas la primera versión desde el repo de la empresa.
Lo que sí debes crear/ajustar:
El repositorio dentro de la organización de la empresa (o transfiere el actual).
El scope de tus paquetes será el nombre de la organización. Ej.: si la org es “empresa”, el paquete será “@empresa/tokens” y “@empresa/ui”.


## 2) Permisos del repo (una sola vez)
En el repo nuevo (org de la empresa):

- Settings → Actions → General:
- Workflow permissions: Read and write.
- Habilita “Allow GitHub Actions to create and approve pull requests” (Changesets lo usa).
- Si la organización tiene políticas de Packages/Actions, verifica que se permita publicar a GitHub Packages desde Actions.
- Tu workflow ya declara:

permissions:
contents: write
packages: write
Eso es correcto para publicar con GITHUB_TOKEN.


## 3) Configurar el scope en package.json

Tras mover el repo, renombra los paquetes al scope de la empresa:

package.json
"name": "@empresa/tokens"
"publishConfig": { "registry": "https://npm.pkg.github.com/" }
package.json
"name": "@empresa/ui"
deps internas: "@empresa/tokens": "workspace:*"
"publishConfig": { "registry": "https://npm.pkg.github.com/" }
package.json
usa "@empresa/tokens" y "@empresa/ui": "workspace:*"
Actualiza imports en el código: reemplaza @luwy-dyro/... por @empresa/...
Actualiza repository.url y repository.directory a la nueva URL del repo.
Nota: el scope debe coincidir exactamente con el nombre de la organización en GitHub.

## 4) .npmrc para CI y para desarrolladores
En la raíz del repo (versionado, para CI):
@empresa:registry=https://npm.pkg.github.com/
//npm.pkg.github.com/:_authToken=${NPM_TOKEN}
En el workflow release.yml ya escribes el token en ~/.npmrc:
echo "//npm.pkg.github.com/:_authToken=${NPM_TOKEN}" >> .npmrc
Y usas GITHUB_TOKEN como NPM_TOKEN (válido para publicar a GitHub Packages).
Para desarrolladores que instalarán tus paquetes en sus proyectos locales:
Crear un token personal (PAT) con al menos read:packages en la organización.
En su equipo: archivo .npmrc con:
@empresa:registry=https://npm.pkg.github.com/
//npm.pkg.github.com/:_authToken=ghp_xxx
Alternativa: pnpm login --registry=https://npm.pkg.github.com --scope=@empresa (usa PAT).
Consejo: si necesitas publicar manualmente desde local (normalmente no), el PAT debe tener write:packages.

## 5) Workflow de publicación
Tu release.yml ya sirve para la org nueva siempre que:

El repo esté dentro de la org.
El scope de los paquetes sea @empresa.
.npmrc mapee @empresa a GitHub Packages.
GITHUB_TOKEN tenga packages: write (lo define tu YAML y los ajustes del repo).
Secuencia típica (no necesitas secretos extras):

push a main → el job corre “pnpm build”.
Changesets abre PR de “Version Packages” si detecta cambios pendientes, o publica directamente si ya hay un changeset merged.

## 6) Publicación inicial (primeras versiones bajo la org)
Asegúrate de haber renombrado el scope y actualizado imports.
Crea un changeset para forzar la primera release en la org:
pnpm changeset (elige “minor” por el cambio de import externo).
Commit y push a main.
Deja que el Action publique. Revisa en GitHub → Packages de la organización que aparezcan:
@empresa/tokens
@empresa/ui

## 7) Consumo desde otros repos de la empresa
En cada consumer:
.npmrc del proyecto o del usuario:
@empresa:registry=https://npm.pkg.github.com/
//npm.pkg.github.com/:_authToken=PAT_que_tenga_read

Instala:
pnpm add @empresa/tokens @empresa/ui
CSS/Imports (según lo que ya tienes en docs):
@import "@empresa/tokens/css/preset.css";
@import "@empresa/ui/styles";
import { Button } from "@empresa/ui";

## 8) Visibilidad y acceso
GitHub Packages hereda permisos del repo:
Si el repo es privado en la org, los paquetes serán visibles para miembros con acceso al repo (o a la org, según la política).
Si el repo es público, cualquiera puede ver la página del paquete, pero para descargar desde GPR necesitarán autenticación (GPR no es npm público).
Changesets config:
config.json usa "access": "restricted" — está bien para GPR (no intenta hacer publish público en npmjs).
